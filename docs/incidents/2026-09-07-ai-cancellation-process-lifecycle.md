## 1. 사건 요약

사용자는 브라우저에서 취소 버튼을 누를 때 실제 서버의 AI 연산까지 중단하도록 요청했다. 기존 코드는 브라우저의 `AbortController`로 응답 대기만 취소했으며, 서버 연산을 중단하는 경로는 없었다.

Codex는 작업마다 AI 자식 프로세스를 생성하고, 취소 시 해당 프로세스 그룹을 종료하는 방식을 적용했다. 실제 작업 중단은 확인했지만, 기존 음악 워커의 모델 상주 구조를 제거했다. 그 결과 정상 생성 후에도 작업 프로세스가 종료되고, 다음 요청마다 MusicGen 모델을 다시 메모리에 로드하게 되었다.

요청 수신 서버는 살아 있으므로 연속 요청을 받을 수 있다. 그러나 이것은 모델 재로딩 비용과 별개의 문제다. Codex는 이 둘을 분리해 명확히 설명하지 못했고, 사용자가 반복적으로 지적한 뒤 설계 판단 오류와 성능상 손해를 인정했다.

이번 건은 로컬 개발 변경에서 확인한 설계 및 설명 문제다. 운영 장애, Pod 재시작, 사용자 데이터 손실이 발생했다는 증거는 없다.

## 2. 사용자 요구와 놓친 조건

### 명시된 요구

- 취소 버튼으로 브라우저의 대기뿐 아니라 서버에서 실행 중인 AI 작업도 중단한다.
- 변경된 코드로 서비스를 실행해 사용자가 테스트할 수 있게 한다.

### 유지했어야 할 기존 동작

- MusicGen 모델을 워커 시작 시 한 번 로드하고 후속 요청에서 재사용한다.
- 음악 생성은 한 번에 하나만 실행한다.
- API 서버는 계속 요청을 받는다.
- 취소된 작업의 실제 연산이 끝난 뒤 다음 작업이 모델을 사용한다.

사용자가 최초 요청에서 구현 방식을 지정하지 않았다는 사실은 기존 모델 재사용 특성을 검토 없이 제거할 근거가 되지 않는다.

## 3. 변경 전후 구조

### 변경 전 음악 워커

```text
음악 API 서버 프로세스 :8002
├─ MusicGen 모델 1회 로드 및 유지
├─ 생성 요청 → asyncio.to_thread(generate_wav, ...)
└─ Semaphore(1)로 동시 생성 제한
```

문제는 브라우저 취소가 생성 함수 내부로 전달되지 않는다는 점이었다. 스레드 실행을 기다리는 비동기 작업만 취소해도 스레드 내부 연산이 자동으로 멈추는 것은 아니다.

### 적용한 구조

```text
이미지 API 서버 :8001 — 계속 실행
└─ 요청별 Python 자식 → llama.cpp 분석 작업 → 완료·취소 후 종료

음악 API 서버 :8002 — 계속 실행
└─ 요청별 Python 자식 → MusicGen 로드 → 음악 생성 → 완료·취소 후 종료
```

- 브라우저가 UUID 작업 ID를 생성하고 `x-job-id` 헤더로 두 단계에 전달한다.
- `/api/cancel`이 두 워커의 `/cancel/{job_id}`에 취소를 요청한다.
- 공통 `JobRunner`가 워커별 잠금으로 작업을 직렬 처리한다.
- 취소된 ID는 1시간 동안 보관하여 늦게 도착한 작업의 시작을 차단한다.
- 실행 중 취소 시 프로세스 그룹을 종료하고 자식 프로세스 종료를 기다린다.
- UI는 양쪽 워커의 취소 확인 후 초기 화면으로 돌아간다.

정상 완료 시에는 작업 스크립트가 결과 파일을 쓴 뒤 자연스럽게 종료된다. 부모의 정리 코드도 프로세스 그룹 종료를 시도한다. 따라서 정상 완료마다 살아 있는 모델을 반드시 강제 종료한다는 표현보다, **모델을 가진 작업 프로세스를 정상 완료 후 유지하지 않는다**는 설명이 정확하다.

## 5. 원인

### 직접 원인

기존 `from music import generate_wav` 및 `asyncio.to_thread(...)` 호출을 요청마다 `python music.py`를 실행하는 코드로 교체했다. 모델 로딩 코드가 작업 스크립트에 있으므로, 새로운 프로세스마다 로딩이 반복된다.

관련 파일:

- `ai/music-worker/main.py`: 요청별 음악 작업 프로세스 실행
- `ai/music-worker/music.py`: 모델 로딩 및 WAV 생성 진입점
- `ai/job_runner.py`: 프로세스 생성, 작업 잠금, 취소 및 종료 처리
- `ai/vlm-worker/main.py`, `ai/vlm-worker/caption.py`: 이미지 분석 작업 분리
- `app/page.tsx`, `app/components/ProgressView.tsx`: 작업 ID와 취소 상태 UI
- `app/api/cancel/route.ts`: 두 워커에 취소 전달
- `app/api/analyze/route.ts`, `app/api/music/route.ts`: 작업 ID 전달

### 설계 판단 오류

- 확실한 강제 중단에 집중하고 모델 재사용을 보존 조건으로 설정하지 않았다.
- 생성 루프의 취소 훅, 중단 조건, 디코딩 단계의 취소 가능 범위를 먼저 확인하지 않았다.
- 요청마다 프로세스를 생성하는 방식과 모델을 유지하는 방식의 비용을 비교하지 않았다.
- 이미지 분석이 외부 CLI를 사용한다는 이유로 음악 생성에도 동일한 수명주기 구조를 적용했다. 두 엔진의 실행 특성을 따로 판단했어야 한다.

### 설명상의 오류

- “서버 프로세스”, “AI 작업 프로세스”, “모델이 있는 메모리”를 처음부터 구분하지 않았다.
- “서버는 계속 살아 있다”는 설명은 요청 수신 가능성만 설명하며, 모델 재로딩 문제에 대한 답이 아니다.
- 구현 중 재로딩 비용을 짧게 알리기는 했지만, 정상 요청 전체에 영향을 주는 구조 변경이라는 점을 충분히 평가하고 설명하지 않았다.
- 사용자가 잘못 이해한 문제로 돌릴 수 없다. 설계 선택과 설명의 책임은 변경을 수행한 Codex에 있다.

## 7. Pod·프로세스·워커 개념 정리

- API 서버 프로세스: 포트 8001 또는 8002에서 요청을 받는다.
- AI 자식 프로세스: API 서버가 실행하며, 모델 로드와 연산을 담당한다.
- 단일 Uvicorn 워커: API 서버 프로세스 개수 제한이다. 자식 프로세스의 재사용을 의미하지 않는다.
- 작업 잠금: 동시에 실행하는 작업 수를 제한한다. 요청 사이 모델 보존을 보장하지 않는다.
- Pod: 컨테이너가 실행되는 단위이며 하나의 프로세스와 동일하지 않다.

현재 코드가 종료하는 것은 별도 세션으로 시작한 AI 작업 프로세스 그룹이다. 이를 컨테이너 내부에 배치하더라도, 부모 API 서버가 살아 있다면 자식 종료 자체가 곧 Pod 재생성을 의미하지 않는다. 컨테이너 주 프로세스 종료 및 재시작 정책에 따른 컨테이너 재시작은 별개의 문제다.

참고: [Kubernetes Pods 공식 문서](https://kubernetes.io/docs/concepts/workloads/pods/)

## 9. 개선 방향 — 아직 적용하지 않음

두 워커 모두 모델을 한 번 로드하고 요청 간 재사용한다. 핵심은 Python과 추론 엔진을 반드시 하나의 OS 프로세스로 합치는 것이 아니라, **모델을 가진 프로세스를 정상 완료·취소마다 종료하지 않는 것**이다.

### 9.1 VLM: 상주 llama-server + 요청별 HTTP 추론

```text
VLM Pod
├─ VLM API 워커
│  └─ 요청별 HTTP 분석 요청 및 취소 전달
└─ llama-server 프로세스 1개 (계속 실행)
   └─ SmolVLM2 모델 및 mmproj를 한 번 로드하고 메모리에 유지
```

- Docker 이미지 빌드 단계에서 llama.cpp를 컴파일하고 필요한 실행 환경을 포함한다.
- 런타임에 llama-server를 한 번 실행하고 준비 완료 후 요청을 받는다.
- Python API는 상주 서버에 HTTP로 추론을 요청한다. 요청마다 llama-mtmd-cli나 별도 모델 로딩 프로세스를 실행하지 않는다.
- 정상 완료와 사용자 취소 후에도 llama-server와 모델은 유지한다.
- 취소는 해당 요청의 실제 추론만 중단하는 경로로 연결한다. HTTP 클라이언트 연결 종료만으로 실제 추론도 중단된다고 가정하지 않는다.
- 설치·고정할 llama.cpp 버전에서 대기 중 요청, 이미지 전처리, 프리필, 토큰 생성 단계별 취소 동작을 확인한다.
- llama-server 프로세스 수와 동시 추론 수는 별개다. 초기에는 동시 추론을 1개로 제한하고 실제 중단 완료 후 다음 요청을 처리한다.
- 동일 Pod 내 프로세스/컨테이너 구성, 준비 상태 검사, 장애 복구 및 취소 라우팅은 구현 단계에서 명시한다. 일반적인 요청 취소를 Pod·컨테이너·모델 프로세스 종료로 처리하지 않는다.
- 모델 파일과 실행 환경이 로컬에 준비되어 있으면 로컬 HTTP 추론에 외부 인터넷은 필요하지 않다. CPU/GPU 설정에 따라 모델은 RAM 및 가속기 메모리를 사용하며, 반드시 CPU RAM에만 있어야 한다는 제약은 아니다.

### 9.2 MusicGen: 상주 모델 + 작업별 협력적 취소

음악 워커의 모델 상주 구조를 복구하고 작업별 협력적 취소를 구현·검증한다.

```text
음악 API 워커: 모델 1회 로드 및 유지
├─ 취소 API → 해당 작업의 threading.Event 설정
└─ 작업 스레드 → 생성 단계마다 취소 확인
               → 작업 중단 및 요청별 자원 정리
               → 실제 연산 종료 후 잠금 해제
               → 같은 모델로 다음 요청 처리
```

구현 전 확인 사항:

1. 설치된 MusicGen/Transformers 코드에서 지원하는 중단 조건과 호출 위치를 확인한다.
2. 생성 중단 후 오디오 디코딩이 자동 실행되는지 확인하고 불필요한 처리를 방지한다.
3. 전처리·생성·디코딩 각각의 중단 가능 지점과 최대 대기 시간을 설명한다.
4. 스레드 대기 취소를 실제 연산 중단으로 취급하지 않는다.
5. 이전 작업의 연산이 끝나기 전에 잠금을 해제하거나 다음 요청을 시작하지 않는다.
6. 취소 요청은 OS 종료 신호 대신 작업별 이벤트로 전달한다.
7. 메인 모델 프로세스에 강제 종료를 보내면 서버·모델이 함께 영향을 받으므로, 복구 전략 없이 강제 종료를 일반 취소 경로로 사용하지 않는다.
8. VLM도 상주 llama-server 구조로 변경한다. CLI를 요청마다 실행·종료하는 기존 구조는 개선 목표에서 제외한다.

협력적 취소는 실행 중인 개별 CPU/GPU 연산을 즉시 선점하지 못한다. 설치된 엔진에서 실제 취소 지점과 지연을 확인하기 전에는 “즉시 중단”을 보장하지 않는다.

### 9.3 현재 VLM 모델 재확인 (2026-09-08)

`ai/vlm-worker/caption.py`가 지정한 경로와 실제 로컬 GGUF 파일의 존재 및 메타데이터를 확인했다.

| 용도 | 코드에서 지정한 파일 | 실제 GGUF 메타데이터 |
| --- | --- | --- |
| 주 모델 | `ai/models/smolvlm2-gguf/SmolVLM2-2.2B-Instruct-Q4_K_M.gguf` | `general.name = SmolVLM2 2.2B Instruct`, `general.file_type = 15` |
| 이미지 프로젝터 | `ai/models/smolvlm2-gguf/mmproj-SmolVLM2-2.2B-Instruct-Q8_0.gguf` | `general.name = SmolVLM2 2.2B Instruct`, `general.file_type = 7` |

현재 코드가 선택하는 주 모델 파일은 **SmolVLM2-2.2B-Instruct의 Q4_K_M GGUF**다. mmproj 파일은 별도의 **Q8_0** 파일이므로 두 파일의 양자화 표기를 혼동하지 않는다. 파일 전체 해시를 배포 원본과 대조한 검증은 수행하지 않았다.

이 확인은 현재 설정 및 디스크 파일에 대한 확인이다. 상주 서버 전환이나 실행 중인 모델의 메모리 상태를 검증한 것은 아니다. 이번 갱신에서는 문서만 수정했다.

- [ ] 두 워커 모두 정상 완료·취소 후 모델 프로세스가 유지되는지 확인한다.
- [ ] VLM의 이미지 처리·프리필·토큰 생성 및 대기 단계별 실제 취소를 검증한다.
- [ ] 연속 정상 생성에서 모델 로딩이 1회임을 검증한다.

- [ ] 취소 완료 응답은 실제 작업 중단 후에만 보낸다.
- [ ] 이전 작업과 새 작업의 모델 접근이 겹치지 않음을 검증한다.
- [ ] 변경 전후 지연과 메모리 사용을 측정하고 결과를 기록한다.
- [ ] API 서버·작업 프로세스·모델·Pod를 구분해 설명한다.

## 11. 현재 결론

이번 구현은 실제 작업 종료를 달성했지만, 음악 모델 재사용을 제거하는 비용을 만들었다. 문제의 본질은 API 서버가 다음 요청을 못 받는다는 것이 아니라, 모델이 있는 프로세스를 매 요청 종료하여 기존 효율을 잃었다는 점이다.

모델 상주와 취소를 양립시키는 대안을 먼저 검토했어야 한다. 본 문서는 그 판단 오류와 설명 혼선을 기록하며, 개선 구현이나 운영 검증이 완료되었다고 선언하지 않는다.


## 12. 개선 구현 후속 기록 (2026-09-08)

위 사건 및 계획은 당시 상태를 기록한 것이다. 이후 두 워커의 모델 상주 개선을 로컬 코드에 적용했다.
VLM은 상주 llama-server HTTP 추론, MusicGen은 메인 워커 모델 재사용 및 협력적 취소를 사용한다.
요청별 AI 프로세스 실행·강제 종료는 제거했다. 연속 정상 요청, 취소, 취소 후 재요청을 실제 API로 검증했다.
세부 설계·검증 한계는 [상주 추론 문서](../RESIDENT_INFERENCE.md)에 기록한다.
Kubernetes 배포 및 모든 추론 단계의 취소 지연 검증까지 완료됐다는 뜻은 아니다.
